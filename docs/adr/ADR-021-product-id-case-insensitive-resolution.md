# ADR-021 — Регистронезависимый резолв `product_id` каталога

- Статус: Accepted
- Дата: 2026-09-07
- Контекст: у инстанса `doravixo.shop` пакеты монет заведены в App Store Connect как
  `100_Tokens_9.99` (заглавная `T`), тогда как каталог `products` засеян строчным
  `100_tokens_9.99` — и сеется он **общей** миграцией для всех инстансов.
- Связанные: [ADR-015](./ADR-015-product-catalog-verbatim-reseed.md) (вербатим-каталог),
  [ADR-019](./ADR-019-adapty-subscription-webhook.md) (второй платёжный контур),
  [ADR-018](./ADR-018-multi-instance-traefik.md) (мульти-инстанс).

## Контекст

`ProductsRepository.get_by_external_id` сравнивал `external_product_id` точно. Это прямое
следствие ADR-015: StoreKit матчит покупку по `product_id` побайтово, поэтому расхождение
строки давало `product is None` → `ignored/unknown_product` → монеты не начислялись.

Мульти-инстанс (ADR-018) сломал допущение, на котором держалось точное сравнение: каталог
общий, а приложений теперь три, и в App Store Connect они заведены **разными людьми в разное
время**. Фактическое состояние на момент решения:

| Инстанс | Регистр в App Store | Подтверждение |
|---|---|---|
| `zavionix.shop` | `100_tokens_9.99` | реальные покупки в `purchases` |
| `norqelia.shop` | — | покупок ещё не было |
| `doravixo.shop` | `100_Tokens_9.99` | подтверждено владельцем |

Общая миграция физически не может засеять оба регистра под одним `external_product_id`.
Любой выбор ломал бы один из инстансов: строчный — витрину и начисления `doravixo`,
заглавный — уже работающий `zavionix` с боевыми покупками.

Регистр значим и для второго контура: Adapty присылает `vendor_product_id` тем же
значением, что и App Store, и `AdaptyWebhookService._coins_for` резолвит его через тот же
репозиторий. То есть один и тот же дефект бил бы по обоим путям начисления.

## Решение

`get_by_external_id` сравнивает через `lower()` с обеих сторон. Каталог остаётся из 7
позиций и остаётся общим; какой бы регистр ни прислали StoreKit или Adapty, он резолвится
в ту же строку.

Инвариант однозначности обеспечивает БД, а не соглашение: миграция `0021` создаёт
уникальный функциональный индекс `uq_products_lower_external_product_id` на
`lower(external_product_id)`. Без него два продукта, различающихся только регистром,
превратили бы `scalar_one_or_none()` в `MultipleResultsFound` прямо на пути начисления
монет — то есть отказ оплаты вместо тихой неоднозначности.

Существующий `uq_products_external_product_id` сохраняется: он остаётся точным ключом для
`ON CONFLICT ON CONSTRAINT` в сид-миграциях каталога.

### Что НЕ меняется

- **Количество монет по-прежнему берётся только из каталога** (`products.grants.coins`).
  Регистронезависимым стал лишь поиск строки; число не выводится ни из payload, ни из имени
  продукта (anti-tamper инвариант ADR-019 §7).
- **Неизвестный продукт остаётся неизвестным.** `totally_unknown_sku` по-прежнему даёт
  `ignored/unknown_product` — послабление касается только регистра, а не сопоставления
  вообще.
- **В `subscription_state.product_external_id` пишется id из каталога**, а не присланный
  вариант написания: иначе одна и та же подписка выглядела бы по-разному в зависимости от
  того, каким контуром пришло событие.
- Фильтр `active` в резолве не применяется — как и раньше, продления старых подписок и
  restore обязаны работать по деактивированному продукту.

## Открытый вопрос: витрина каталога

`GET /v1/billing/products` отдаёт `external_product_id` **в том регистре, в каком он лежит в
БД** — то есть строчном. Начисление это не ломает (резолв регистронезависим), но если
клиент берёт идентификаторы из этого ответа и запрашивает по ним продукты у StoreKit, то на
`doravixo` StoreKit ничего не найдёт: там продукты называются с заглавной `T`, а витрина
запросит строчные.

Вопрос не закрыт, потому что зависит от клиента: если iOS хардкодит `product_id`, проблемы
нет вовсе. Если берёт из API — понадобится **per-instance каталог** (свой набор
`external_product_id` на инстанс через seed/env вместо общей миграции), что является
отдельным решением и заметной переделкой. Зафиксировано как **Q-021-1**.

## Последствия

- Миграция `0021` — только индекс, данные не трогаются. `downgrade` снимает индекс.
- Попытка добавить продукт, отличающийся от существующего лишь регистром, теперь падает с
  `IntegrityError` на уровне БД. Это намеренно: молча схлопнуть два продукта в один нельзя,
  оператор обязан решить, какой верный.
- Покупки, уже совершённые на `zavionix` со строчным регистром, не затронуты: их дедуп и
  ledger-ключи строятся по `transaction_id`, а не по `product_id`.
